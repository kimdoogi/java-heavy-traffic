## 목표
- E3 수행: CPU bound(`/api/cpu/hash`)에서 VT on/off 차이가 없음(혹은 VT 약간 손해)을 실측.
- E2와 대조: I/O bound에선 쓰레드 수가 병목 → CPU bound에선 CPU가 병목이라 VT가 도움이 안 됨을 수치로.

## 범위 / 하지 않는 것
- M(1cpu)·L(2cpu) × VT on/off = 4런. S는 필요 시 추가.
- CPU 스케일링 확인(L=2cpu가 M의 ~2배인지)까지. pinning(E5)은 다음 작업.

## 진행 기록 (시간순)
- 시작: 트랙 A 첫 작업. 스택 기동 후 단발 요청으로 `/cpu/hash?n=20000` 비용 측정 → MAX_RPS 산정 → 4런.
- 빌드 실패: 로컬 JDK 21 소실 → [P-001](../problems/P-001-jdk21-missing-build-fail.md). settings.gradle에 foojay resolver 추가로 해결.
- k6도 소실돼 있었음(1차 4런 전부 `k6: command not found`, exit 127인데 run-experiment.sh가 exit 0 — 관찰만, 추후 개선 후보). `brew install k6` → v2.2.0.
- 단발 비용: warm 후 ~6.5–8ms/req → 1cpu 천장 ≈ 140rps 추정. MAX_RPS 기본 400으로 4런(M/L × on/off) 실행.
- 1차 4런 결과: 전부 피크 ~400rps 소화(peak30s 396.9~400.0) — **추정 빗나감, 실 비용 ≈ 2.5ms/req(JIT 완전 워밍업 후)**. 천장 미도달. 단 M에서 on/off 차이 관찰: M-off p50 239.5ms·CPU 99.5%(포화·큐잉) vs M-on p50 11.3ms·CPU 71.3%. 가설(무차이)과 다른 신호 — 2차에서 천장 확인 필요.
- 2차: M×on/off MAX_RPS=800, L×on/off MAX_RPS=1200으로 천장 탐색 (`E3-M-{on,off}-800`, `E3-L-{on,off}-1200`).
- 2차 결과 — **가설 뒤집힘. CPU bound에서도 VT가 처리량·지연 모두 우위**:
  - M 피크30s: on **760.6** vs off **493.6** rps. avg 460.9 vs 367.2. p50 2.7ms vs 896.3ms. dropped 1,997 vs 15,701(maxVUs 2000 cap 도달).
  - L 피크30s: on **1,194.9**(목표 소화) vs off **1,058.1**. p50 1.4ms vs 2,043ms.
  - 가설(수정): 차이의 원인은 VT 자체가 아니라 **활성 스레드 수** — 플랫폼은 200 스레드가 1~2 CPU를 타임슬라이싱(컨텍스트 스위치·캐시 오염 오버헤드)하고, VT는 캐리어 스레드=CPU 수라 오버서브스크립션이 없음.
  - 검증 컨트롤 런: `E3-M-off-800-t2` — 플랫폼 + `TOMCAT_MAX_THREADS=2`. 이게 VT 수준으로 나오면 "스레드 수" 가설 확정.

- 컨트롤 결과: `E3-M-off-800-t2` 피크 **799.4rps·p50 1.4ms·dropped 203** — VT(760.6)보다도 좋음. **가설 확정: 변수는 스레드 수.**
- [E3 실험 페이지](../experiments/E3-cpu-bound-vt-vs-platform.md) 작성, 9런 완료 (1차 4 + 천장 4 + 컨트롤 1).

## 결과
- E3 완료. M(1cpu) 피크: 플랫폼200 493.6 / VT 760.6 / 플랫폼2 **799.4** rps. L(2cpu): VT 1,194.9(부하 상한 도달).
- 결론: CPU bound에서 기본 플랫폼(200)이 지는 건 오버서브스크립션 탓. VT는 캐리어=CPU 수라 기본값으로 이김. 튜닝된 플랫폼 ≥ VT.
