## 목표
- VT + `synchronized` + I/O(sleep)에서 캐리어 pinning으로 처리량이 급락함을 재현하고, `ReentrantLock` 교체로 회복됨을 실측.
- `-Djdk.tracePinnedThreads=full`로 pinned 스택 증거 확보.

## 범위 / 하지 않는 것
- VT on 고정, M(1cpu=캐리어1)·L(2cpu=캐리어2) × sync/lock = 4런. pinned 천장이 캐리어 수에 비례하는지까지.
- JDK 24(JEP 491) 실측 비교는 안 함(기록만).

## 진행 기록 (시간순)
- 첫 PR 흐름 작업(`a/e5-pinning`). `load/22-pin.js` 생성 (PIN_MODE=sync|lock, PIN_MS 기본 50).
- 예측: pinned 천장 = 캐리어 수/(0.05s) → M ≈ 20rps, L ≈ 40rps. lock은 E2 수준(수천).

- 4런 완료. pinned 스택 확보(`reason:MONITOR`, `pinSync:82 <== monitors:1`).
- 예측 빗나감: sync 천장이 M/L 동일 37.5rps(예측 20/40) → [P-003](../problems/P-003-pinned-ceiling-not-scaling.md) open으로 기록.

- (08-25) PR #1 셀프 리뷰(Claude Code) 11건 → 반영. 최대 건: lock 런 pinned-count(M=1, L=2)가 직전 sync 런 잔재 — 컨테이너 로그로 재검증해 0건으로 정정, [P-005](../problems/P-005-pinned-count-carryover.md) solved. 검증 명령(그대로):
  - `docker inspect -f '{{.Created}}' heavy-coupon-api-1` → `2026-08-24T02:35:31Z`(= L-sync 시작 11:35:31 KST, 이후 재생성 없음)
  - `docker logs -t heavy-coupon-api-1 2>&1 | grep -n 'reason:MONITOR'` → 2건: `02:35:40Z`, `02:38:20Z` — 모두 L-sync 구간(L-lock 시작 11:38:42 이전)
- (08-25) 당시 pinned 로그 수동 추출 명령을 journal에 남기지 않았음(규칙 위반, 원인 규명 지연의 원인). 사용 형태는 `docker logs heavy-coupon-api-1 2>&1 | grep -A20 'reason:MONITOR'`(traces) / `grep -c`(count)로 추정 — 다음부턴 실행 즉시 기록.
