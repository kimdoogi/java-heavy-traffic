## 맥락
- 목적은 "Java 21 버츄얼 쓰레드로 대용량 트래픽을 리소스 제한 하에 견디는지 실험 + 학습 + 이직 포트폴리오".
- 버츄얼 쓰레드는 **I/O 대기가 많은 워크로드**에서만 효과가 있고 CPU bound에선 차이가 없다. 따라서 도메인 자체가 I/O 대기와 경합을 포함해야 실험이 의미 있다.

## 선택지
1. **선착순 쿠폰 발급 (+ 느린 외부 연동)** — 장점: DB 쓰기 경합(락 전략 비교) + 외부 I/O 대기(VT 효과) 둘 다 포함, 국내 백엔드 면접 단골 주제 / 단점: 도메인 구현량이 약간 있음
2. URL 단축기 — 장점: 단순 / 단점: 읽기 위주라 VT 효과·동시성 제어 학습이 약함
3. API Aggregator(여러 하위 서비스 호출 합치기) — 장점: VT 효과가 가장 극적 / 단점: 동시성 제어 학습이 빠짐
4. 채팅/알림(WebSocket) — 장점: 재미 / 단점: VT보다 다른 주제가 커짐

## 결정
- 1번. 단, 실험용 엔드포인트(`/io/sleep`, `/cpu/hash`, `/pin/sync` 등)를 별도로 둬서 3번의 "순수 VT 효과"도 고립시켜 측정한다.

## 이유
- 하나의 도메인으로 "VT 효과", "동시성 제어", "외부 장애 대응", "병목 전이"를 모두 실험할 수 있다.
- 면접에서 설명하기 좋은 주제.

## 결과 / 영향
- PLAN.md §1의 엔드포인트·전략 설계가 이 결정을 따른다.
- 재검토 조건: 구현량이 실험 진행을 막을 정도로 커지면 조회/발급 2개 API로 축소.
