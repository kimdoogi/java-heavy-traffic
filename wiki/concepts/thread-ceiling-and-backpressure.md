## 한 줄 정의
- 블로킹 서버의 최대 처리량은 `쓰레드 수 / 요청당 대기시간`으로 천장이 생기고, 이 천장은 병목이자 **의도치 않은 백프레셔**다. VT는 천장을 제거하지만 백프레셔도 함께 제거한다.

## 왜 중요한가 (이 프로젝트에서)
- E2 실측: Tomcat 200 threads × 300ms 대기 → S/M/L 모두 661~667 rps (이론 666.7). CPU 4배 증설도 무효.
- VT는 1 CPU에서 2,000 rps(p99 316ms)를 소화했지만, 0.5 CPU에선 포화 후 **무제한 수용 → 백로그 폭주 → 3,000건 60s 타임아웃**. 같은 조건의 플랫폼은 느리지만(5.7s) 실패 0%.

## 동작 원리
- 플랫폼: 요청당 OS 쓰레드 1개 점유. 블로킹되면 쓰레드가 놀고, 풀이 다 차면 새 요청은 큐에서 대기 → **동시성 상한 = 풀 크기** (Little's law: L = λ×W → λ_max = 풀/W).
- VT: 블로킹 시 캐리어 쓰레드에서 unmount되어 캐리어가 다른 VT를 실행 → 동시성 상한이 사실상 메모리/CPU. 단, **수용량 제한이 사라지므로 도착률 > 처리율이면 대기 요청이 무한 누적**된다.

## 이 프로젝트에서 직접 확인한 것
- [E2](../experiments/E2-io-bound-vt-vs-platform.md) 표: 천장 666 실측, 대기열 지연 4.5s = 2800/666+0.3 계산 일치, S-on 붕괴.

## 면접 답변 버전 (30초)
- "블로킹 MVC 서버의 처리량 천장은 쓰레드 수÷요청당 대기시간입니다. 실험에서 Tomcat 200쓰레드에 300ms I/O를 걸면 CPU와 무관하게 666rps에서 막히는 걸 확인했고, 버츄얼 쓰레드를 켜면 같은 1코어에서 2,000rps까지 지연 열화 없이 처리했습니다. 다만 쓰레드 풀이 해주던 암묵적 백프레셔가 사라지기 때문에, 0.5코어 환경에선 VT가 오히려 무제한 수용 끝에 타임아웃 폭탄으로 무너지는 것도 재현했습니다. 그래서 VT 도입 시 타임아웃·세마포어·레이트리밋 같은 명시적 과부하 방어가 필수라고 답하겠습니다."
